아래의 조건을 모두 적용하여, 아래의 요구사항을 모두 구현할 것.
구현 결과를 체크리스트로 반환할 것.

==============================================

조건-커서룰) 아래의 커서룰을 적용하여 작업하고, 이 작업이 끝나면 해당 rules 적용 결과를 체크리스트로 반환할 것.
	- Service Layer는 오케스트레이션만 수행한다
	- Domain 로직 직접 구현 금지
	- 캐시 전략은 Service에서 구현 (캐시 조회 → fallback → 저장)
	- Repository/Domain에 위임하여 조립
	- 단일 public 함수만 export
	- throw 사용 최소화
	- Cold Start 포함 모든 경우에서 결과 반환
	- 객체 mutation 금지 (immutability 유지)

==============================================

조건-파일경로) 참고 및 기준 파일 경로는 다음과 같다.
	- 구현 대상:
		- src/services/match/getHomeMatches.service.ts
	- 의존 Service/Repository:
		- src/services/match/getMatchCandidates.service.ts
		- src/services/match/calculateMatchResult.service.ts
		- src/repositories/matchResultsCache.repository.ts
		- src/repositories/userProfiles.repository.ts
		- src/repositories/userStatus.repository.ts
	- 참고 패턴:
		- src/services/match/calculateMatchResults.service.ts

==============================================

조건-구현참고) 반드시 참고할 기존 구현 패턴은 다음과 같다.
	- getMatchCandidates.service.ts는 후보 목록 조회 (채팅/친구/차단 제외)
	- calculateMatchResult.service.ts는 1:1 매칭 계산
	- matchResultsCache.repository.ts는 캐시 CRUD
	- 캐시 우선 조회 + 실시간 fallback 전략 사용
	- 프로필/상태 정보는 별도 함수로 추가 (enrichWithProfiles)

==============================================

핵심요구사항) 다음 기능을 step-by-step으로 구현하고, 각 항목의 적용 여부를 체크리스트로 반환할 것.

0) 파일/Export 규칙
	- 파일 위치: src/services/match/getHomeMatches.service.ts
	- 단일 public 함수만 export: getHomeMatches
	- default export 금지, named export만 허용
	- 내부 헬퍼 함수는 private으로 (export 안 함)

1) 함수 시그니처 (고정)
	- 함수명: getHomeMatches
	- 입력:
		- client: SupabaseClient<Database>
		- viewerId: string
	- 반환:
		- Promise<EnrichedMatchResult[]>
		- EnrichedMatchResult 타입:
			{
				target_id: string
				score: number
				reasons: any
				tags: any
				computed_at: string
				profile: { userId, nickname, animalType, avatarUrl }
				status: 'online' | 'away' | 'dnd' | 'offline'
			}

2) 캐시 전략 (핵심 로직)
	- 처리 흐름:
		1. getMatchCandidates로 후보 조회 (채팅/친구/차단 제외)
		2. 후보 없으면 즉시 [] 반환
		3. matchCacheRepo.findByViewer로 캐시 조회
		4. 캐시가 4개 이상이면 상위 4개 즉시 반환 (enrichWithProfiles 적용)
		5. 부족하면:
			- 캐시되지 않은 후보 중 필요한 개수만큼 선택 (최대 8개 - 캐시된 개수)
			- calculateMatchResult로 실시간 계산
			- 계산 결과를 matchCacheRepo.upsert로 저장
		6. 캐시 + 실시간 결과 병합
		7. 점수순 정렬 후 상위 4개
		8. enrichWithProfiles로 프로필/상태 추가
	- 실패 처리:
		- 개별 계산 실패는 로그만 남기고 계속 진행
		- null 결과는 필터링하여 제외

3) enrichWithProfiles 헬퍼 함수 (internal)
	- 함수명: enrichWithProfiles
	- 입력:
		- client: SupabaseClient<Database>
		- results: CachedMatchResult[]
	- 동작:
		- userProfilesRepo.findByUserIds로 프로필 조회
		- userStatusRepo.findByUserIds로 상태 조회
		- getAvatarImagePath로 아바타 경로 계산
		- Map으로 변환하여 빠른 조회
		- 각 결과에 profile, status 필드 추가
	- 반환: EnrichedMatchResult[]

4) 금지 사항 (강제)
	- MatchContext 직접 조립 ❌
	- Domain factor 함수 직접 호출 ❌
	- 점수 계산 로직 직접 구현 ❌
	- 온라인 필터링 ❌ (홈 화면은 온라인 여부 무관)
	- 정렬은 점수순만 (온라인 우선 정렬 ❌)
	- throw 남용 ❌ (개별 실패는 로그만)
	- null / undefined 반환 ❌ (항상 배열 반환)
	- mutation 금지 (push, Object.assign ❌)

5) Cold Start 대응
	- 후보는 있으나 데이터 부족한 경우에도 계산 시도
	- Cold Start 결과도 그대로 배열에 포함
	- Cold Start를 예외로 취급하는 분기 ❌

6) Immutability 규칙
	- Repository 반환값 직접 수정 ❌
	- map / filter 중심으로 새 배열/객체 생성
	- 반환 객체는 항상 새로운 객체 리터럴

7) 의존성 규칙
	- 허용 의존:
		- getMatchCandidates
		- calculateMatchResult
		- matchResultsCache.repository
		- userProfiles.repository
		- userStatus.repository
		- getAvatarImagePath
	- 금지 의존:
		- UI / Hook / Store ❌
		- Domain 타입 직접 의존 ❌

8) 성능 최적화
	- 병렬 조회 사용: Promise.all([profiles, statuses])
	- Map으로 변환하여 O(1) 조회
	- 필요한 개수만 계산 (최대 8개까지만)
	- 캐시 hit 시 실시간 계산 스킵

구현 완료 후 반환) 아래 체크리스트를 반드시 반환할 것.
	1. Service 정체성

	4. 캐시 전략
		- 캐시 우선 조회
